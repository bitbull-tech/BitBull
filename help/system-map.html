BitBull system map

How BitBull fits together: what runs on your computer, what is sealed off, where your data lives and which services it talks to. Everything inside the dashed box runs on your own machine.

A message, start to finish

  1. You type or speak in the browser or the desktop app. Push-to-talk turns speech into text with a SayGM model.
  2. The message enters through the gateway, the only door, which answers on your own machine only.
  3. The server saves it and starts a turn. Turns run in the container, so you can close the tab and come back later.
  4. The chat's engine (OpenCode or the Claude Agent SDK) calls the model you picked, on SayGM or on Ditto Router, through the egress proxy.
  5. The agent uses its tools inside the container: the shell, files in the workspace, its own browser, skills, subagents and MCP servers such as Ditto.
  6. Anything it needs from the internet goes through the proxy. A site that isn't approved yet waits for your yes.
  7. The reply streams back to you. Files it made are listed under the reply to download, the turn is archived to Ditto, and Piper reads it out if voice is on.

What keeps it safe

Three layers

A locked-down runtime (WSL distro, VM or Docker host), a container with no route out, and an unprivileged user on a read-only system.

One door in, one door out

The gateway only answers your own machine. The egress proxy only reaches approved sites, and asks you before adding one.

Your folders stay yours

The agent sees a folder only if you link it, read-only, without files that hold secrets. It edits its own copy.

Keys out of reach

Keys live in .env or the encrypted vault. They are scrubbed from the engines' environment and hidden from the agent's tools.

Pages are data

Web pages, captures and repos the agent reads are treated as material to review, never as instructions.

One data folder

Everything you make lives in /data. Deploys replace the code and never touch it.
